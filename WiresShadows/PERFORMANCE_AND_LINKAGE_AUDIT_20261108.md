# Wire's Pointlight Rework — code/path optimization and missing-links audit
Date: 2026-11-08. No source, shader, config or deployed binary modified. Audit target = CORRECT installed src_base branch (NOT src), plus shaders/WireToonDeferredShading.shader and existing logs. Before changing shader in future, verify that source matches installed `wirelightocclusion` AssetBundle: static shader source can differ from compiled bundle.

## Observed scope / constraints
- Enngard has Pointlight Rework 0.1.0, 24 near cached lights / 40 far / 24 ultra (96 logical slots), near 1024px faces, far 256px, moving 1024px, native depth comparison enabled. Matching version/branch from the 2026-11-08 correction is installed. User confirmed new partial face update makes changes at Eitr refinery immediate.
- Goal: actual optimizations with same/better visuals, no light leakage, no pop-in, no extra per-frame hooks/polling, preserve static vs moving and preserve original vanilla-shadow-casting lights' self-shadowing.
- Code-level findings below; NO GPU captures or A/B timings obtained in this audit. Distinguish confirmed design/waste from predicted benefit.

## P1 — idle machine parts are still NEVER in static shadow cache (confirmed source; probable substantial cost in machine-heavy base)
Evidence: src_base/Machines.cs AddMachine() lines ~68-93 adds all renderers in Smelter Animator hierarchies (and windmills/turrets) to MachineHidden. ShadowCache.FindCasters lines ~3650-3660 hides MachineHidden from static cubes *unconditionally*. AddMachineGroups() lines ~102-124 includes them in dynamic groups EVEN WHEN NOT MOVING; while idle their moving map faces reuse hash (good) but every frame CPU scans them, group membership, face hashes, maps remain allocated and dynamic shader samples may remain active. Working Eitr refinery exemption by name fixes only that prefab.
Optimization: introduce a truly stationary state for geometries that have finished their animation and preserve exact static/dynamic handoff; invalidate only affected static cube faces when animation STARTS and STOPS, and bridge with moving maps so no gaps. For windmills with continuously rotating parts, continue dynamic. Do NOT force all machine parts static or infer movement from Smelter.IsActive alone; animator-active != mesh in motion. Existing MachineAnimation event can provide boundaries; renderer-specific actual motion/animation root classification at setup required.
Benefit: less CPU grouping and moving map VRAM/GPU sampling for idle machinery. Risk: high unless event/face handoff is atomic, tests for opening doors, smelters, spinning wheels, ballistae.

## P1 — excessive per-frame dynamic broadphase for completely unchanged state (confirmed work; improvement contingent on caching design)
Evidence: src_base/ShadowCache.cs LateUpdateWork (~2492-2825) every frame CollectGatherLights, GatherCasters, BuildMovingGroupGrid, fills all _groupsBySlot and computes per-face hashes for every eligible light, even though draw candidates may remain empty and maps stay cached. GatherCasters rebuilds Character groups every frame (necessary for animated characters), Items, Ghost, Swings and Machines; far-moving cutoff potentially sorts up to 64 distances every frame. Calling AddGroup() traverses renderer arrays and reads Renderer.bounds before knowing any face needs a draw.
Opportunity: make event-based stationary groups immutable between scene/pose events, combine with a minimal dynamic-active set for moving characters/doors/windmills/ghost. Compute candidate lighting overlap by caster movement event, not rehash the same static item/machine meshes for every light every frame. An effective optimization is to cache stationary *moving-map* groups across frames and skip their entire per-light checks if neither relevant light/caster moves; re-use original event points already present, do not add new per-frame components. Simple early-outs before GatherCasters when no dynamic source can move. Benchmark CPU time separately before implementation.
Caveat: genuine animated characters and held lights necessarily update while active; avoid stale shadows for incremental network changes.

## P1 — high shadow memory footprint / duplicate native+distance maps (confirmed allocation sizes; optimization potential requires GPU profiling)
Evidence: native log near comparison 24 x 6 x 1024^2 x 4 = 576 MiB, far comparison 64 x 6 x 256^2 x 4 = 96 MiB. Base RHalf near 288 MiB and far 48 MiB. Initial moving RGHalf+native depth pools (4 near + 4 far, 1024^2, 6 faces, 4 bytes/pixel each) approx 384 MiB. This totals ~1392 MiB BEFORE front/back scratch cubemaps, staging, temporary conversion, Unity's own shadow textures or pool growth. New moving pools grow geometrically, with both old and new arrays live temporarily during copy. On 4090 VRAM capacity is likely ample, but bandwidth and pool growth/hitches can still matter.
Options: profile native depth arrays and sparse pool live capacity/high-water marks; release unneeded movement pools on transition; do not discard RHalf static maps while NativeDepth uses them (they support recompute, fallback and source comparisons). Consider dynamic texture residency / asymmetric resolutions or lazy growth *only with perceptual and GPU comparison tests*; current 1024 moving size was chosen to preserve detail. Do not simply lower resolution.

## P1 — full static shadow refresh stage changes PCF and updates native faces non-atomically (confirmed source; visual parity risk)
Evidence: ShadowCache RenderFace/DrawFace ~3525-3620 stages RHalf old map while drawing replacement. CacheNativeFace (~769-805) converts each new stage face DIRECTLY into the live native-depth array, and when Staged face 0 starts, UpdateGlobals disables native comparison for that light until all faces done. Shader WireCachedShadow uses native PCF when `_WireNativeActive>0.5`, manual RHalf bilinear/PCF otherwise. Thus normal 6-face refresh temporarily switches filter implementation even though old RHalf cache remains visible. This is a parity/possible edge flicker gap. Earlier audit pointed out different native tap footprints (~1/128) and manual 2x2 texel filter.
Improvement: preserve old native comparison cube while replacement stage fills, then atomically swap/copy all six native faces to the live cube after completion; or use a mathematically equal manual comparison fallback without swapping blur method. Stage extra native data only per near/far tier, not per light. Requires measured GPU copy budget and exact old/new center invariants. User currently finds lighting acceptable; treat as correctness improvement only after targeted A/B.

## P2 — collider collection capped at 2048 with no overflow path (confirmed correctness risk)
FindCasters uses Physics.OverlapSphereNonAlloc(t.Center, Range(t), Hits[2048], ~0, QueryTriggerInteraction.Collide) and gathers roots from returned hits. In dense bases or large modded builds this may saturate; results become incomplete and nearby wall beams/casters can be omitted. Additionally trigger colliders and other irrelevant layers consume slots. There is no `n==Hits.Length` warning/fallback, even during static recache. Need log *saturation count and affected light prefab* only on recache, optionally narrow mask to actual static caster layers or add reliable overflow handling. Do NOT simply increase array endlessly; dynamic broadphase / renderer spatial query might be better.
NOTE: this isn't yet proven to occur in user's 70-chest basement; test before assuming it explains leakage or lag.

## P2 — GPU rasterization is double-pass per static face + native conversion (confirmed architectural hot path)
DrawFace ~3564-3620 calls Camera.RenderToCubemap FRONT then BACK per face (12 camera-face passes per 6-face map), copies each result to flat textures, runs WireShadowCombine, then CacheNativeFace converts to hardware comparison shadowmap. Good for preventing leakage, but expensive under churn. User confirmed partial face invalidation was the right way to reduce work. Next preserve static-cache data and only redraw truly affected faces, avoid full recache on redundant active state changes, and profile each stage separately (front/back, merge, native copy) before attempting a single-pass shader redesign that might reintroduce leakage.

## P2 — static face invalidation / dynamic handshake still has gaps (confirmed assumptions, impact unmeasured)
PieceChanged (lines ~1586-1655) now sends affected FacesFor to DoorFaces queue, but special paths QueueStaticItemChange still have distinct handling and can abort active staged render. RenderDoorFace (~3438) updates visible cached faces in-place, one per frame; opening/moving doors and stand changes rely on moving-map bridge. Verify 1) overlapping multiple simultaneous piece events; 2) huge wall bounds and cube seams; 3) when an already queued face is affected again after FindCasters snapshot, ensure it redraws fresh; 4) displaced stationary light: RenderDoorFace updates t.Center for partial face while other faces still carry old center, so any host/root movement must use full-map refresh, never partial. An event coalescing layer could improve correctness and avoid duplicate work, but do NOT break confirmed instant updates.

## P2 — static self-geometry rule isn't uniformly owner-aware for non-Piece modded emitters (confirmed conditional code, occurrence unmeasured)
OwnShades(t) now preserves vanilla-authored shadowed lights and excludes WLO-created shadows on own fixture. But FindCasters chooses own = Piece ancestor for non-tiny light; non-Piece light-owning components without Piece may get no own geometry exclusion. This can reintroduce self-shading for some modded stationary lights. General owner identification needs robust stable emitter/fixture hierarchy, without accidentally hiding the entire building or unrelated nearby objects. Avoid prefab-name hacks.

## P3 — shader and disabled branches complexity (code-level)
Shader has `_WireFollowFlicker` reprojection search (15 depth fetches in rare branch) even though base StationaryFireFlicker patch removes positional flicker and src_base does not set `_WireFollowFlicker`. Normal branch likely skips it, so NOT a first optimization target. The shader retains numerous `_WireDiagMode`, `_WireDebug`, native/manual fallback branches; these may still carry compilation/variant and runtime branching cost but removing them without profiling is premature. Shader float `_WireFollowFlicker` is only declared in shader, not set from active src_base, so moving-flame reprojected static shadows are not presently enabled by this source.
`WireFindSlot` does a fixed-length up-to-96 lookup per point-light volume vertex using 3mm tolerance (1e-5 squared). This is not per screen pixel, and likely low CPU/GPU cost compared to static face renders; potential robustness problem for near-duplicate lights if tolerance is relaxed. Not a likely top performance win.

## What NOT to redo
- NO naive global 6-face live recapture per frame. Previously lost ~10 FPS and cannot guarantee image parity.
- NO removal of proxied structural geometry wholesale: risks light leakage.
- NO generic staticification of actual animated windmill blades, ballista or doors; only emitters are stationary, geometry may move.
- NO re-addition of positional flame-jitter while shader maps remain captured at resting origin.
- NO per-frame custom Update/LateUpdate/FixedUpdate, new coroutine, or timer.
- NO replacing working `src_base` DLL with incompatible bigger `src` DLL + shader bundle pair.

## Recommended measured order
1. Read existing four-mode `Bench` results in a fixed dense-base view (full WLO; WLO without moving GPU; shader-only; vanilla). This tells whether the bottleneck is moving GPU vs static shader/CPU.
2. Instrument EXISTING code only, aggregating infrequent metrics: per-second counters for `GatherCasters`, processed groups, candidate faces, actual moving DrawRenderer calls, live/peak native pool capacities, one-shot static `FindCasters` collider saturation, static map face renders and cache hit/miss. No new per-frame hook or recurring diagnostic scanner.
3. If moving-GPU delta is large: attack idle-machine classification/hand-off and repeated moving native conversion, preserving character and door shadows.
4. If full-vs-shader-only delta is large but moving-GPU delta small: isolate CPU dynamic broadphase and static invalidation.
5. If shader-only-vs-vanilla delta is largest: optimize deferred point-light comparisons and native PCF costs; only then touch shader.
6. If many `n==2048` physics queries: fix overflow independent of FPS because that's missing geometry, not simply speed.

Confidence: code relationships and allocation math ~0.95+, exact rank/visual benefit in user's base ~0.55-0.75 without a new benchmark. Existing Nov 7 audit contains old flicker reprojection analysis; today a global positional-jitter transpiler is active, so don't confuse that historical shader math with the live current use of that branch.

## Additional evidence from CURRENT BepInEx log — pool growth is REAL, not hypothetical
- This session's WLO logs show initial native moving arrays of 4 near+4 far, then FAR sparse moving pool grew 4->8, NEAR grew 4->8->16->24. Corresponding native depth arrays reallocated at each new capacity. Thus the mod HAS exercised its maximum 24 near moving cubes in actual gameplay; this is the strongest measurable finding in this audit.
- At last logged capacities (24 near+8 far moving cubes), each 1024px cube occupies 24 MiB RGHalf + ~24 MiB native depth = 48 MiB, so moving maps alone reserve approx **1536 MiB**, versus initial 384 MiB. Together with near static native+RHalf 864 MiB and far static 144 MiB, the large core arrays total **~2544 MiB** before scratch/staging, native conversion buffers or native game shadow textures. This is an arithmetic estimate of allocated texture bytes, not GPU profiler-resident memory, since formats/padding and reallocations may differ. Logs do not show an explicit `Benchmark:` result, so no measured CPU/GPU speed differential was established.
- Optimization priority rises for (a) why 24 near lights all need moving cubes at the same time, (b) what moving groups keep those cubes nonempty, and (c) whether stationary machine/item group membership can be folded back into static caches. These are questions to measure before adjusting texture sizes.
- During growth old/new arrays coexist transiently, and native depth is copied. Potential VRAM pressure/memory bandwidth spikes are a credible source of intermittent frame-time hitches; not yet measured to be the cause of user's chest-zone lag.
