## Actual data path, reconstructed without trusting comments
1. `LightFlicker.CustomUpdate` moves the real light transform by a trigonometric `m_offset * m_movement`, and updates intensity. WPR no longer injects movement.
2. `ShadowCache.RenderFace` (~3472–3492) captures static geometry from `RestingPosition(t.Light)`, NOT the current flame position, for all six faces. `DrawFace` (~3495–3540) renders front- and back-facing radial depth in two `Camera.RenderToCubemap` passes per face. `WireShadowCombine` (line ~45) uses back-before-front or midpoint/35cm cap.
3. Near-plane proxy/structural geometry is drawn into the static map (`ShadowCache.FindProxies` ~3848 and `DrawUntagged` ~365). That can introduce nearby depth values that are not the actual visual mesh's depth.
4. Existing static cubemap is stored in the near or far cache; optional **native hardware comparison** converts the radial distance into a separate shadowmap-format cube using `WireShadowNativeDepthCopy`. `UpdateGlobals` publishes the map center, ready and native-active flags.
5. The existing main-camera `Camera.onPreCull` callback, `RunFrame` (~2825–2843), publishes the current light positions in `_WireLightNow`. Deferred shader `WireFindSlot` (~247–257) identifies its corresponding shadow cube by a close world-position match.
6. `WireCachedShadow` (shader ~283–379) reads receiver vector `v = receiver - cachedCenter` and `delta = currentLight - cachedCenter`. Its moving-shadow branch does **not** render from current light: it searches rays `v`, `v+delta`, `v+3*delta`, selects their minimum blocking depth `s`, and warps the old lookup using `v + delta * (r/max(s,0.05)-1)`. The shader then tests that direction against the **old** cube with comparison distance `r = |receiver-cachedCenter|`.
7. Moving character/gate/item maps use a separate, direct current-light origin; their face hashes and updates are tracked in `LateUpdateWork` (~2480–2770). They use native comparison depth or manual PCF and multiply with the static result.
8. The existing near-tier promotion mechanism keeps the old far map until its full-resolution successor is ready. Keep this intact; it is not intrinsically responsible for flame shadow wobble.

## Ranked findings

### 1. Core reprojection is not a geometrically valid light-space transform (critical; confidence 0.98)
`WireToonDeferredShading.shader` lines 283–379. For each **receiver pixel**, choose the minimum among unrelated cube depths `a0, a1, a2` (and potentially 12 fallback rays), then multiply the light displacement by `r/s - 1`. Changing which ray or which blocker supplies the minimum changes the estimated warp **discontinuously** and across neighboring pixels. The warped depth query is not an actual depth capture from the displaced light. A single resting-origin depth cube cannot reveal occluded geometry at a new origin.

**Numerical sensitivity:** with `r=4m` and `|delta|=0.05m`, displacement magnitude is `0.15m` at `s=1m`, `0.95m` at `s=0.2m`, `3.95m` at `s=0.05m`. These are exact consequences of the implemented expression, **not measured in-game**.

This explains a credible mechanism for silhouette contraction, jumps and wild moving edges, especially where competing blockers have very different depth. It is the primary architectural defect to target. Another tweak to ray count, threshold, or best-error heuristic cannot guarantee mathematical parity.

### 2. Collider proxies are an amplifier, not merely an occlusion aid (high; 0.94 for mechanism, lower for impact on particular sconce)
`ShadowCache.FindProxies` (~3848–3880) inserts nearby wall/floor colliders and structural collider copies. `WireShadowFront/Back` cut real mesh inside `_WireNearCut`, but retain certain proxy back-face depths there. These can yield a short `s`. The shader then specifically prefers the **minimum** such `s` and divides by as little as 0.05m. This combination can magnify a small flame movement enormously. The proxy geometry helps stop leaks, so deleting proxies wholesale is **not** an appropriate fix.

### 3. Native/static PCF filter footprints differ, including during a staged refresh (high; 0.96)
The dominant static path uses native comparison when `_WireNativeActive[slot] > 0.5` and manual `WireStaticBilinear` otherwise (`WireToonDeferredShading.shader` ~361–378). Native taps use **fixed `1/128` offsets** (~68–74), irrespective of whether the near map is 1024px and the far map is 256px. At a dominant cube-face coordinate near 1, `1/128` is about **4 near-tier texels**. Manual bilinear taps use the actual map resolution and true adjacent texels. These are *different blur and edge footprints*, not equivalent implementations. 

`ShadowCache.UpdateGlobals` (~2393–2403) disables native comparison for a ready light while `t.Staged`. On stage completion it may re-enable it. That swaps PCF methods even with a stable light. It can alter perceived sharpness abruptly during recaches. This is separate from the per-frame sway bug; frequency depends on recache events.

### 4. Moving map and shader can temporarily disagree on origin (high; 0.94)
`LateUpdateWork` around lines 2590–2650: for stationary moving casters, when only the **flame** position changes, an existing moving-face map redraws on a staggered **every-fourth-frame** condition. But `WireCachedShadow` (~355–356) computes the moving-map sampling vector from the **current** light origin every frame. Between those updates, the stored cubemap is from the previous origin, and the shader reads it as if it were current. This can create stepped or jumping shadows of characters, doors, mounted items or other moving-map casters; it does **not** directly explain static plank silhouettes if those planks are exclusively in the static map.

### 5. Old map may be exposed with a newly published center during staged recaches (medium-high; 0.9 for logic, case dependent)
`RenderFace` (~3472–3490) sets `t.Staged` for a ready light, then immediately assigns `t.Center = RestingPosition(t.Light)` **before** all six new staged faces are complete. `UpdateGlobals` uses that same mutable `t.Center` as the old map's origin; the old map stays visible until `FinishMap`. If the captured center actually moved (e.g. host/root transform changes), the old cube may be interpreted against a new origin before the swap. Typical static sconce resting position should not move, so **this is not proved to be the source of ordinary flicker pumping**.

### 6. Extremely tight per-light slot matching is a separate possible disappearance source (medium; 0.75)
`WireFindSlot` shader ~247–257 checks `dot(_LightPos - _WireLightNow[i], ...) < 1e-5` (approx **3.16mm** tolerance). The C# slot position is copied at main camera pre-cull. If actual deferred-light-volume position and uploaded position differ due to update timing/mods/precision, the light may receive **no** cached shadow that draw. This can explain a whole-light instantaneous leak/pulse, not local shape deformation. Need empirical confirmation before changing threshold: loosening could cause collisions among nearby distinct lights.

### 7. A full origin re-render really is expensive in this renderer (confirmed design; 0.99)
One complete six-face static cube uses **12 `Camera.RenderToCubemap` face renders** (front/back per face), then copying/combining and native-depth conversion. Repeating one whole cube every gameplay frame was the failed implementation; user observed ~10 FPS drop. Doing this for all lights is not viable. This confirms why merely rendering native/current-position cubemaps without a targeted strategy is the wrong next step.

## Other code reviewed and not implicated by evidence
- `Plugin.cs`: bundle loading, deferred shader swapping, flame-follow global and quality keywords; four active settings only.
- `Bench.cs`: four-mode CPU/GPU-impact comparison; it deliberately changes cache/shader settings and is not a shadow-quality fix.
- `Machines.cs`: machine/turret groups and animation-driven moving casters; separate from static wall/plank projection.
- `VpoCompat.cs`: removes a VPO LightFlicker Awake patch; no direct shadow reprojection.
- ShadowCache light lifecycle / slot priorities / soft/near promotion, event-driven door and item handoffs, dynamic sparse pools, native-depth copies, shader global uploads and culling. These may have their own edge cases but should not be changed without linked evidence.
- `WireFabricDepthMerge`, `WireShadowDistance`, `WireShadowFront`, `WireShadowBack`, `WireShadowCombine`, `WireShadowNativeDepthCopy`: inspected their data representations and interactions; none can make a single rest-origin depth cube contain unknown occluder visibility from a new viewpoint.

## Recommendation for next engineering step
1. **Do not change any live source, settings or shader yet.** Save a known-good baseline and establish mathematical requirements for the target static shadow edge under a moving light. Work from explicit geometry, not heuristic depth minima.
2. In an **offline CPU mathematical test** (not another debug toggle in-game), compare rays from the actual moving light through a few simple synthetic box/wall meshes with the current shader's projected-shadow results. Include near-plane proxy depths, discontinuities, varying receiver depth, cubemap seams, and movement in all three axes. Do not claim parity without a ground-truth test.
3. Decide how to supply **sufficient geometry** for a correct displaced light. A single depth cubemap is information-theoretically insufficient; possibilities include rendering only camera-contributing shadow faces with a proper staging and fixed-origin invariant, or a separate geometry-aware ray/occluder representation. Benchmark geometry collection and GPU submission costs before changing the gameplay shader.
4. Make static-origin and moving-caster-origin semantics consistent. Preserve existing non-destructive near promotion, no-light-leakage collider proxies, no per-frame arbitrary renderer switches, and no extra user-facing toggles.
5. Treat the native/static PCF footprint and the every-fourth-frame moving-map temporal mismatch as **separate, bounded fixes** after the core geometry model is sound.

**Bottom line:** The old shadow-warp algorithm is the main *design flaw*, and the min-depth / near-proxy interaction is the strongest *specific* source-level mechanism for the visible shape pumping. The exact in-game contribution is not yet measured. Previous shader-sampling patches and repeated whole-cube recaptures did not solve it; both were inappropriate ways to pursue parity.
