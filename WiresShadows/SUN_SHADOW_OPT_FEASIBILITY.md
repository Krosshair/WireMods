# WPR: Sun-shadow optimization feasibility (RESEARCH ONLY)
Date: 2026-11-08. No WPR shader, DLL, or game config modifications for this investigation.

## Conclusions
**Yes, an engine-native sun shadow caster optimization route exists in this exact Valheim/Unity runtime.** Unlike past PCSS prototypes, this can reduce the work of building sun shadow maps rather than adding expensive shadow-map samples. A meaningful FPS improvement remains UNPROVEN until layer occupancy and GPU timings are measured.

Most promising API: UnityEngine.Light.layerShadowCullDistances (Directional light only). Unity 6000.0 documentation: https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/light/layershadowculldistances . It takes a float[32] (one distance per object layer), and 0 means original behavior for that layer; null disables. This culls caster draw work only, not camera-visible geometry. Camera.layerCullDistances may interact; the most restrictive value wins. An object outside the camera can still cast a visible long shadow, especially with sun low: DO NOT naively use camera view distance as shadow-caster distance. Avoid altering terrain, Default, building and tree layers without scene tests.

**Verified against REAL game assembly on KajetanGOAT:** D:\SteamLibrary\steamapps\common\Valheim\valheim_Data\Managed\UnityEngine.CoreModule.dll, decompiled UnityEngine.Light; the property getter, setter and native bindings GetLayerShadowCullDistances / SetLayerShadowCullDistances exist. This is not an assumed new engine feature. WPR point shadows are entirely separate. WPR source ShadowCache.cs static mask includes Default, static_solid, Default_small, piece, piece_nonsolid, terrain, blocker; moving mask includes character, character_net, character_ghost, character_noenv, item, ragdoll. These are WPR mask choices, NOT a measured histogram of SUN shadow casters. Some layers (especially Default and piece) mix critical visible casters; inspect actual renderers/layer occupancy before choosing distance targets. Layer masks alone do not distinguish small vs huge objects inside a shared layer.

**Verified actual Valheim sun owner:** EnvMan.m_dirLight (Light), decompiled from game assembly. EnvMan.SetEnv recomputes sun rotation from m_smoothDayFraction and env.m_sunAngle and positions directional Light relative to main camera each update; the light orientation continuously moves. Therefore copying the static-point-light shadow cache strategy for directional sunlight is UNSAFE: cascaded projection changes with camera and sun, causing staleness/ghost shadows. EnvMan.UpdateEnvironment sets dirLight.renderMode = ForceVertex inside interiors, ForcePixel otherwise; an optimization should preserve this behavior. Use the already registered EnvMan lifecycle events rather than any new per-frame component polling: attach a one-time sun culling array on EnvMan sun light registration/recreation, restore exact original array on disable/OnDestroy. This proposal needs C# proof-of-life and in-game validation; no patch was made now.

### Why per-layer culling is a better test than PCSS
- It reduces geometry submitted for shadow-map GENERATION when casters exceed allowed distances, rather than adding samples to the full-screen shadow lookup. Shadow quality/geometry remains exactly vanilla for non-culled layers and casters, unlike PCSS.
- Does NOT need custom ScreenSpaceShadows shader, additional shadow map/cubemap, artificial softening, per-frame Update/FixedUpdate or new GPU pass.
- Might deliver 0 gain if relevant layers already culled by engine, few eligible objects exist, GPU is dominated by shading/WPR/storage, or camera distance settings supersede it. Needs measurement; do not assert FPS improvement.
- Most promising cautiously eligible layers: incidental small clutter/particle vegetation where their shadow cannot perceptibly contribute after some distance. Preserve all larger building/tree/terrain shadow casters initially. Actual Valheim layer names and renderer counts still need a single diagnostic classification pass to verify eligibility.
- Test on sun near horizon, big buildings, forest canopy, mountain, interiors and near/far camera. At low angles an object beyond the camera frustum can cast a shadow far into the visible scene. Default=0 for all critical layers is mandatory until verified.

### Other optimization routes and caveats
1. Standard QualitySettings.shadowDistance/shadowCascades/shadowCascade4Split changes are straightforward but affect shadow quality/range and may visibly pop/change resolution; useful benchmarking controls, not identical-visual optimizations. Unity manuals: https://docs.unity.com/en-us/engine/6000.0/manual/lighting-overview/shadows/shadow-realtime/shadow-cascades/use and https://docs.unity.cn/560/Documentation/Manual/DirLightShadows.html .
2. Separate static/dynamic sun-map caching is theoretically possible but relatively high-risk in rotating sun plus moving camera; needs stable projection matrices, atlas-aware invalidation and dynamic-caster compositing. DO NOT attempt blindly: WPR already had ghost-shadow trouble.
3. A custom sun shadow filtering shader will not save shadow map caster draw calls, and PCSS normally increases per-pixel GPU cost; user rejected it.
4. HDRP GPU Resident Drawer/renderer graph GPU occlusion features cannot simply be imported into Valheim's Built-in pipeline. Feature comparison: https://docs.unity.com/en-us/engine/6000.0/manual/render-pipelines/choose-a-render-pipeline/feature-comparison .
5. Instrument using a reproducible nighttime/daytime/same-camera comparison (when directional sun effectively noncontributing), GPU frame captures / GPU profiler when possible and render marker timing. Record FPS, GPU ms, CPU draw/render thread, sun shadow render pass cost, caster batch count. Use existing tools, no new per-frame logger in WPR. Establish a baseline BEFORE any new culling. A/B identical camera/time/weather, no variable effects.

### Suggested independent implementation path (NOT BUILT)
A. One-time scene-layer diagnostic: layer id/name, count of shadow-casting renderers and approximate size distribution for visible and far objects; specifically identify which layers mix essential and incidental casters. Data via one-time scan on request or event-based registry; no periodic scene scans.
B. Baseline GPU profile sun cascade render passes in open forest vs player-built base and mountain near low-sun altitude. Quantify whether sun renders are actually a bottleneck.
C. Optional reversible prototype: set Light.layerShadowCullDistances for ONE proven safe distant clutter layer only, all other 31 layers 0; preserve original array. Event-driven install via EnvMan ownership, no per-frame code, independent opt-in setting and deterministic rollback.
D. Visual parity test including long shadows and sun angles, then benchmark identical camera/lighting scene with/without culling. Only expand conservative distance targets if real gains and no missing shadow shapes. Sun optimization benchmark should not be bundled with other light effects.

## Separate idea: subtle indirect firelight (NOT IMPLEMENTED)
Aim for gentle warm surface glow without changing stationary shadow shapes and without adding global ambient or leak-prone unshadowed fill lights.
- Low-cost first stage: local receiver-surface warm spill INSIDE the EXISTING WPR deferred point-light shader, modulating very weak diffuse illumination only where the existing cached shadow already confirms direct path. This can enhance walls/floors near fireplaces cheaply, but is NOT a physically accurate second bounce and must not be called realtime GI.
- More credible second bounce: at light registration / geometry-changed events, cast 2–3 rays to nearby floor/walls, cache surface hit, normal and approximate albedo; compute weak tinted lobes on physically adjacent surfaces in existing lighting path. Actual bounce->receiver visibility cannot be inferred from the light's original single cubemap and MUST be guarded, or the effect will leak through walls. A shadow-casting secondary Light would be costlier and potentially break WPR. No new per-frame scans/coroutines.
- Do not globally increase fire intensity or shadow brightness: user disliked those experiments. Make independent disabled-by-default test if explicitly requested.
- Unity Built-in supports Enlighten precomputed GI in some setups, but Valheim's dynamic user buildings and rapidly changing fire/sun make it an unsuitable assumption for realtime bouncing. This source assessment is a WPR-specific engineering inference, not a tested Valheim GI profile.
